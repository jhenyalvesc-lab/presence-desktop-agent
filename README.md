# Presence Desktop Agent

Processo local (Electron + Node/TypeScript) do Presence — Fase 10 do backend (`PROJECT_SPEC.md`, repositório principal `presence-37deb226`). A arquitetura completa (stack, separação de processos, wake word, controle do computador, WhatsApp, permissões, riscos) foi auditada e aprovada antes de qualquer código — ver `IMPLEMENTATION_STATE.md` no repositório principal.

## Escopo implementado

**Fase A** — fundação + pareamento de dispositivo:
- Processo Electron com Main Process, Tray (bandeja) e uma janela de status mínima.
- **Fechar a janela nunca encerra o agente** — só esconde. Sair de verdade é só pelo item "Encerrar" da bandeja.
- **Iniciar com o Windows** (autostart), configurável pela própria bandeja.
- **Pareamento com o backend cloud** por código de 6 dígitos — reaproveita integralmente os endpoints já implementados no repositório principal (`/api/presence/agent/pair/start`, `/pair/status`), sem nenhum mecanismo paralelo.
- **Armazenamento seguro da credencial do dispositivo** via `safeStorage` do próprio Electron (cofre do SO — DPAPI no Windows), nunca em texto puro em disco, nunca exposta ao renderer.
- **Ping** — prova o round-trip credencial-de-dispositivo → nuvem (`/api/presence/agent/ping`) antes de qualquer capacidade mais arriscada.

**Fase 10B** — Audio Worker + Wake Word ("Presence"):
- **Audio Worker isolado** (`electron.utilityProcess`, `src/audio/audio-worker.ts`) — processo separado do Main, sobrevive a crash sem derrubar o resto do agente. Captura contínua de PCM via `@picovoice/pvrecorder-node`.
- **Wake Word Engine** (`src/audio/wake-word-engine.ts`), wrapper sobre `@picovoice/porcupine-node`. **"Presence" é uma keyword custom — não vem pronta no Porcupine.** Ativar de verdade exige duas coisas pessoais, que este código nunca fabrica nem simula:
  1. Uma **AccessKey gratuita** da conta da Jheny no [Picovoice Console](https://console.picovoice.ai/).
  2. Um **arquivo `.ppn`** da keyword "Presence" treinado nesse mesmo console, exportado para Windows.

  Configure via variáveis de ambiente antes de `npm run start`:
  ```
  PICOVOICE_ACCESS_KEY=<sua-access-key>
  PRESENCE_WAKE_WORD_KEYWORD_PATH=<caminho-para-o-arquivo-.ppn-treinado>
  PRESENCE_WAKE_WORD_SENSITIVITY=0.6   # opcional, 0–1
  ```
  Sem essas variáveis, o Audio Worker continua rodando normalmente (mic ativo) e a janela mostra "wake word não configurada" em vez de travar ou fingir que está ativa.
- O Main Process nunca processa PCM diretamente — só recebe eventos discretos do worker (`status`, `wake_detected`) via `audio-manager.ts`, exibidos na janela de status.
- Encerrar pela bandeja para o Audio Worker de forma limpa antes de sair.

**Fase 10C** — Duas palmas:
- **Detector de transiente em DSP puro** (`src/audio/clap-detector.ts`), sem lib pronta (não existe uma equivalente ao Porcupine pra isso) — plugado no mesmo laço de frames do Audio Worker, sobre o mesmo stream de PCM que já alimenta o Wake Word, sem um segundo pipeline de áudio. Detecta um pico de amplitude ("onset"), ignora a cauda/reverberação da mesma palma (debounce) e confirma "duas palmas" só quando um segundo onset aparece dentro de uma janela de tempo configurável depois do primeiro.
- **Ligado por padrão** (ao contrário do wake word, não depende de nenhuma credencial externa) — mas com falsos positivos/negativos esperados nesse tipo de detector, por isso a sensibilidade e a janela de tempo são configuráveis via variáveis de ambiente:
  ```
  PRESENCE_CLAP_ENABLED=true          # false desativa a detecção de duas palmas
  PRESENCE_CLAP_SENSITIVITY=0.5       # 0–1, mais alto = mais sensível (mais falsos positivos)
  PRESENCE_CLAP_MIN_GAP_MS=150        # menor intervalo aceito entre as duas palmas
  PRESENCE_CLAP_MAX_GAP_MS=600        # maior intervalo aceito entre as duas palmas
  PRESENCE_CLAP_DEBOUNCE_MS=100       # tempo mínimo entre dois onsets distintos
  ```
- Validado com um harness sintético (frames de PCM simulando silêncio/palmas com timestamps controlados) cobrindo 5 cenários: par dentro da janela detecta, uma palma isolada nunca detecta, intervalo maior que o máximo não conta como par, a cauda da mesma palma não vira uma segunda detecção, e som abaixo do limiar de sensibilidade não dispara — os cinco passaram.

**Fase 10D** — Voice Mode / interação por comando (STT):
- Quando a wake word ou as duas palmas disparam, o agente entra em modo de escuta e captura o próximo comando falado via um **STT Renderer** dedicado (`src/stt-window.ts` + `renderer/stt.js`) — uma `BrowserWindow` oculta que usa a Web Speech API do próprio Chromium embutido no Electron. **Exceção explícita e temporária ao Local-First** (já prevista na arquitetura aprovada): esse reconhecimento manda o áudio pros servidores do Google, não roda localmente.
- **Risco adicional, descoberto durante esta implementação, não coberto pela auditoria original:** builds "unbranded" do Chromium — como o do Electron — costumam não ter a chave de API do Google que a Web Speech API depende pra funcionar de verdade em produção (limitação conhecida do Electron, documentada em várias issues públicas do projeto). Só um teste real no Windows confirma se funciona; se não funcionar, a alternativa já prevista na arquitetura original é Whisper local (`whisper.cpp`).
- `src/voice-interaction.ts` orquestra o ciclo: wake word/duas palmas → "ouvindo" → captura via STT → texto do comando exposto pro Main/UI. **Só captura e mostra o texto nesta fatia** — executar o que foi pedido é escopo da Fase 10E (Tool Registry), ainda não implementada.
- Validado com `tsc --strict`/build limpos e execução real do Electron sob `xvfb-run`: a janela do STT é criada, a página roda `recognition.start()`, e o resultado (aqui, `not-allowed` — sem microfone/permissão real neste sandbox) volta corretamente por IPC até `captureVoiceCommand()`, sem travar nem derrubar o processo; o app completo (Tray + Audio Worker + Voice Interaction) sobe e permanece de pé sem erro.

**Fase 10E** — Tool Registry + execução de ações no Windows:
- **Tool Registry** (`src/tools/registry.ts`): única fonte de verdade de quais ferramentas existem e qual o nível de risco de cada uma (`read_only`/`reversible`/`external_comm`/`destructive`) — nesta fatia é só metadado; quem de fato aplica os 4 níveis (bloquear/confirmar) é o Permission Manager, implementado na Fase 10F (ver abaixo).
- **App Registry** (`src/tools/app-registry.ts`): tabela local, específica da máquina, lida de `config/app-registry.json` (`.gitignore`d — cada máquina tem a sua; um `config/app-registry.example.json` documenta o formato). Vem **vazia por padrão** — nunca inventamos caminhos reais de apps do computador da Jheny; ela precisa preencher esse arquivo com os aplicativos dela.
- **Ferramentas Nível 0 (leitura)**: `list_processes` (`tasklist`/`ps`), `list_windows`, `read_file`, `ocr_screen`.
- **Ferramentas Nível 1 (reversível, executam sozinhas)**: `open_app` (resolve por alias no App Registry, `child_process.spawn`), `focus_window`, `take_screenshot`, `move_mouse`/`click_mouse`/`type_text` (mouse/teclado).
- **`close_window` registrada como `destructive`** de propósito — a API de janelas não tem um "fechar" de verdade (só minimizar/restaurar/maximizar), então fechar significa encerrar o processo, podendo perder trabalho não salvo; sempre exige confirmação (Fase 10F), mesmo assim não é chamada por nada nesta fatia.
- **Resolvedor determinístico de comando** (`src/command-resolver.ts`): só cobre "abre/abra/abrir X" contra o App Registry — exatamente o caso que a arquitetura descreve como resolvível sem IA. Liga com `voice-interaction.ts`: comando capturado → tenta casar contra o App Registry → se casar, executa `open_app` via o Execution Engine (Fase 10F) e reporta o resultado; se não casar, só mostra o texto (nada é executado, sem tentar adivinhar).
- **Achados reais desta implementação, documentados e não escondidos:**
  1. `@nut-tree/nut-js` (nome citado na arquitetura original) **não existe mais no npm** (`404` confirmado) — o projeto migrou pro fork ativamente mantido `@nut-tree-fork/nut-js`, usado aqui no lugar. Internamente usa `libnut`, um módulo **N-API** (portável entre versões de Node/Electron, ao contrário de bindings tradicionais).
  2. `node-window-manager` só suporta oficialmente **Windows e macOS** — o próprio pacote marca Linux como `~~Linux~~ (WIP)`. Não pôde ser validado de ponta a ponta neste sandbox Linux (só confirmado que carregar o módulo e chamar `getWindows()` não derruba o processo — devolve uma lista vazia).
  3. `node-window-manager` compila via `node-gyp` no `npm install` (não é N-API), visando o ABI do Node do sistema — **não o do Electron** (confirmado aqui: Node do sistema usa `NODE_MODULE_VERSION 127`, o Electron desta versão usa `130`). Isso é um risco real de a `.node` compilada não carregar dentro do Electron em produção. Por isso: `@electron/rebuild` foi adicionado como devDependency e `npm run rebuild-native` (`electron-rebuild -f`) deve ser rodado uma vez depois de `npm install` e antes de `npm run start` — não automatizado como `postinstall` de propósito, porque rebuildar módulos nativos exige ferramentas de compilação (Python + toolchain C++, no Windows via Visual Studio Build Tools) que podem não estar presentes na máquina, e um `postinstall` que falha quebraria até um `npm install` básico.
  4. `screenshot-desktop` **trava (nunca resolve nem rejeita)** neste sandbox quando falta uma ferramenta de linha de comando do X11 que ele depende (`xrandr`) — confirmado ao vivo. Por isso `take_screenshot`/`ocr_screen` agora passam por um limite de tempo (`src/tools/timeout.ts`, 10s/30s) — nunca travam a interação por voz inteira à toa. No Windows real a captura usa APIs nativas, não `xrandr`; esse modo de falha específico é bem provável de ser só do sandbox, mas o limite de tempo é uma proteção real de qualquer forma.
- **Validado ao vivo, com um App Registry de teste temporário**: `tsc --strict`/build limpos; execução real sob `xvfb-run` confirmou `list_processes` (85 processos reais listados), `read_file` (conteúdo real de um arquivo), `move_mouse`/`click_mouse`/`type_text` (nut-js/libnut controlando o cursor/teclado de verdade contra o display virtual — sucesso real, não simulado), `take_screenshot`/`ocr_screen` estourando o limite de tempo de forma limpa (o achado real #4 acima), e o fluxo completo "abre o teste" → resolução por alias → `open_app` → processo de verdade spawnado (confirmado por um arquivo criado pelo processo filho).

**Fase 10F** — Permission Manager + confirmação + Audit Log:
- **Permission Manager** (`src/permission-manager.ts`): aplica os 4 níveis de risco definidos no Tool Registry, exatamente como a arquitetura descreve — Nível 0 (leitura) e Nível 1 (reversível) sempre executam sozinhos; Nível 2 (comunicação externa) é configurável (`setExternalCommMode("auto" | "confirm")`, padrão `"confirm"` — nunca assume permissão implícita); Nível 3 (destrutivo) **sempre** exige confirmação, não é configurável.
- **Execution Engine** (`src/execution-engine.ts`): único caminho pra rodar uma ferramenta de verdade — pede confirmação quando exigido, roda a ferramenta, e grava tudo no Audit Log (sucesso, negação ou erro). `command-resolver.ts` foi atualizado pra passar por aqui em vez de chamar `tool.run()` direto.
- **Confirmação** (`src/confirmation-broker.ts`): quando uma ferramenta precisa de aprovação, a janela de status é trazida pra frente automaticamente e mostra um card "Confirmação necessária" com botões Aprovar/Negar. Sem resposta em 30s, **nega por segurança** (nunca assume aprovação por timeout).
- **Audit Log LOCAL** (`src/audit-log.ts`) — arquivo JSONL no perfil do usuário + card "Log de auditoria" na janela mostrando as últimas ações (ferramenta, nível de risco, resultado). **Isto não é o log de auditoria completo na nuvem** (`agent_audit_log`) previsto na arquitetura — esse é escopo de uma fase futura ("Permissões + auditoria completa"); esta fatia é só o registro local que prova que toda execução passa pelo Permission Manager.
- **Validado ao vivo de ponta a ponta, incluindo cliques reais na janela** (não simulados na lógica): sob `xvfb-run`, ferramentas de teste registradas para cada nível confirmaram — Nível 0/1 executam sem mostrar o card de confirmação; Nível 3 mostra o card, e um clique real em "Aprovar" (via `webContents.executeJavaScript` simulando o clique do usuário) libera a execução, um clique real em "Negar" bloqueia; Nível 2 no modo padrão (`confirm`) também exige confirmação, e depois de mudar pra `auto` executa sozinho. O Audit Log final refletiu corretamente cada uma dessas seis execuções.

**Fase 10G** — Scheduler + Notification Manager:
- **Scheduler** (`src/scheduler.ts`), `node-cron` dentro do Main Process, exatamente como a arquitetura descreve — 100% local e determinístico pra disparar; `scheduleJob(id, cronExpression, handler)`/`cancelJob(id)`, com status por job (última execução, sucesso/erro, próxima execução) exposto na janela.
- **Notification Manager** (`src/tools/notification-tools.ts`, tool `show_notification`, Nível 1) — usa a própria `Notification` API do Electron, sem lib nova.
- **Primeira automação real**: um job `cloud-healthcheck` (padrão a cada 15 min, configurável via `PRESENCE_HEALTHCHECK_CRON`) chama o `pingCloud()` já existente (Fase A) e, se falhar, mostra uma notificação local via o Execution Engine (Fase 10F) — prova o Scheduler de ponta a ponta **reaproveitando um contrato de nuvem já existente**, sem inventar endpoint novo.
- **Lacuna real, sinalizada e não preenchida sozinha**: sincronizar calendário/lembretes de verdade (a intenção original da arquitetura pra esta sub-fase) exigiria um **endpoint novo, autenticado por dispositivo**, pra buscar `calendar_events`/`reminder_rules` — isso não existe hoje (o único contrato de dispositivo é pareamento/ping) e não foi criado nesta fatia por decisão deliberada: seria um mecanismo de nuvem novo, decisão que cabe à Jheny confirmar, não inventar sozinho no meio da implementação sequencial. Fica registrado como pendência.
- **Validado ao vivo**: sob `xvfb-run`, com uma expressão de cron acelerada só pro teste (a cada 2 segundos), o job disparou de verdade repetidas vezes, `pingCloud()` falhou (sem credencial pareada neste sandbox — `presence-agent/not-paired`, não um bug), e a notificação de falha foi mostrada de verdade via o Execution Engine a cada disparo, tudo registrado corretamente no Audit Log e no status do job.

**Fase 10H** — Claude Code / Git / GitHub:
- **Git** (`src/tools/git-tools.ts`, Nível 0): `git_status`/`git_log`/`git_branch`/`git_diff`, via `child_process` num diretório informado (`{cwd}`) — 100% determinístico, sem IA, exatamente como a arquitetura descreve.
- **GitHub** (`src/tools/github-tools.ts`, Nível 0): `github_pr_status`/`github_actions_status`, chamada REST direta à API do GitHub. **Exige um token pessoal da Jheny** (`GITHUB_TOKEN`) — uma credencial externa que este código nunca fabrica nem simula, mesmo princípio já usado pra AccessKey do Picovoice (Fase 10B): sem o token, lança `presence-agent/github-token-missing` em vez de fingir sucesso.
- **Claude Code** (`src/tools/claude-code-tools.ts`, Nível 0), duas capacidades bem diferentes em confiabilidade:
  1. `claude_code_process_status` — filtra `list_processes` (Fase 10E) por um padrão de nome configurável (`PRESENCE_CLAUDE_CODE_PROCESS_PATTERN`, padrão `"claude"`). **Ambiguidade real**: o nome exato do processo no Windows da Jheny não é algo que este código possa garantir de antemão.
  2. `claude_code_confirmation_check` — a arquitetura aprovada já é explícita que **isto não tem solução garantida**: "não existe uma API genérica pra ler o que está escrito num terminal arbitrário". Implementado como heurística best-effort, não uma capacidade resolvida: acha uma janela cujo título bate com um padrão (`list_windows`, Fase 10E), tira um screenshot, roda OCR nele (`ocr_screen`, Fase 10E), e testa o texto contra padrões reais de prompt de confirmação do próprio Claude Code CLI (`❯ 1. Yes`, `(y/n)`, "Do you want to proceed?", "Press Enter to continue"). Cada etapa dessa cadeia pode falhar silenciosamente — o resultado é sempre rotulado como heurística.
- **Validado de verdade**: `git_status`/`git_log`/`git_branch` rodaram contra o próprio repositório `presence-desktop-agent` (branch/commits/status reais, não simulados); `github_pr_status` sem `GITHUB_TOKEN` lançou o erro claro esperado, em vez de fingir sucesso; `claude_code_process_status` — sem fabricar nada — detectou de verdade um processo real chamado `claude` rodando no ambiente onde este código foi escrito; a heurística de confirmação (`checkConfirmationHeuristic`, função pura) foi testada com 5 casos sintéticos (3 prompts reais de confirmação, um progresso de build, uma string vazia) — os 5 bateram com o esperado.
- **Agente Universal, Fase G (v0.2.9)** — a peça que faltava não era a ferramenta local, era o elo conversacional: essas 8 ferramentas já existiam e já estavam no Tool Registry, mas (1) `response-composer.ts` não sabia descrever nenhum resultado delas (caía no genérico `${label}.`, que é a INTENÇÃO gerada pelo Planner antes de rodar, nunca o resultado real) e (2) o prompt de `desktopCommandAction` (repositório principal) não dava nenhum exemplo desse tipo de pergunta. Fechado nesta fase: `describeToolResult` ganhou casos reais pra todas as 8 (fala o processo/pid encontrado, a estimativa honesta de confirmação, o texto real de `git_status`/`git_branch`/`git_log`, um resumo — nunca o diff inteiro — pra `git_diff`, e o resultado real de PR/Actions do GitHub); `git_status`/`git_log`/`git_branch`/`git_diff` e `github_pr_status`/`github_actions_status` ganharam `cwd`/`owner`/`repo`/`branch` opcionais com fallback pra variáveis de ambiente (`PRESENCE_DEFAULT_REPO_PATH`/`PRESENCE_DEFAULT_GITHUB_OWNER`/`PRESENCE_DEFAULT_GITHUB_REPO`, `branch` cai pra `"main"`) — pergunta natural tipo "qual o status do meu projeto?" não devia exigir caminho/repo explícito toda vez. Nenhuma ferramenta nova de execução (rodar build local, matar processo) — tudo continua `read_only`, mesmo escopo de leitura da Fase 10H.

**Fila de comandos nuvem→dispositivo** (roteiro original da arquitetura, "Fase F" — não confundir com a Fase 10F acima, que é Permission Manager):
- **Lado de nuvem** (`agent_commands`, `claim_next_agent_command`/`complete_agent_command`, rotas `/api/presence/agent/commands/poll`/`/complete`) já existia no repositório principal (`presence-37deb226`) desde uma entrega anterior. **Este repositório implementa o lado cliente**: `src/command-queue.ts` faz polling curto (padrão 4s, configurável via `PRESENCE_COMMAND_POLL_INTERVAL_MS`) contra `/poll` — só quando o dispositivo já está pareado (nunca chama a nuvem sem credencial, evitando um erro previsível em loop).
- **Zero mecanismo paralelo**: um comando recebido passa pelo mesmíssimo `command-resolver.ts`/`execution-engine.ts` que a voz (wake word/duas palmas) já usa — mesmo Permission Manager, mesma confirmação quando exigida, mesmo Audit Log. Um comando que não bate com nada conhecido é reportado como `failed` pra nuvem (nunca fica preso em `delivered`, nunca finge sucesso).
- Reaproveita `cloud-client.ts` (`pollNextCommand`/`completeCommand`, mesmo padrão de `pingCloud()`) e `device-store.ts` já existentes.
- **Validado**: `tsc --strict`/build limpos; execução real do Electron sob `xvfb-run` por 12s sem exceção — sem credencial pareada neste sandbox, o poller nunca chama a nuvem (comportamento esperado, não testado o caminho de sucesso). Tentativa direta de round-trip real contra o endpoint de produção (`curl` através do proxy configurado neste ambiente) falhou por isolamento de rede do sandbox — mesma limitação já documentada em todas as fases anteriores (nenhuma sessão aqui alcança `*.lovable.app`/`*.supabase.co` diretamente); o teste real de ponta a ponta (comando digitado em Settings → Desktop Agent chegando até aqui e sendo executado) depende de um Windows real pareado.

**Planner** (roteiro original da arquitetura, "Fase H" — tarefas compostas):
- **Decisão arquitetural que o documento aprovado deixava em aberto** (só dizia "decomposição por IA", sem mecanismo — o Desktop Agent nunca segura um JWT de sessão, só uma credencial de dispositivo, então não podia simplesmente chamar `askPresence` como o app web faz). Perguntada explicitamente, a Jheny escolheu: um **novo endpoint de nuvem device-autenticado** (`POST /api/presence/agent/plan`, repositório principal, mesmo padrão de `verifyAgentDeviceCredential` já usado por ping/fila de comandos) que chama o mesmo Lovable AI Gateway já usado por `askPresence` — nenhum mecanismo de IA paralelo.
- **Só é chamado como fallback**: quando o resolvedor determinístico (`command-resolver.ts`) não bate com nada, `src/planner.ts` monta o catálogo de ferramentas realmente disponíveis nesta máquina (`listTools()`, Fase 10E, com uma dica de formato de args por ferramenta — e pro `open_app` especificamente, a lista real de apps do App Registry local) e pede à nuvem pra decompor o comando numa sequência de passos.
- **O backend nunca executa nada** — só propõe `{tool, argsJson, label}` por passo. A validação de segurança real acontece na hora de executar: cada passo passa pelo MESMO Execution Engine que qualquer outra execução (Permission Manager, confirmação quando exigida, Audit Log) — um nome de ferramenta inventado pelo modelo falha com `not_found`, nunca é confiado antes disso. Passos rodam em sequência e **param na primeira falha** (malformado, negado ou erro) — um plano de vários passos tipicamente depende do anterior ter funcionado.
- Wireado nos dois pontos de entrada de comando que já existiam: `voice-interaction.ts` (voz — quando o determinístico não casa, cai pro Planner antes de só mostrar o texto) e `command-queue.ts` (fila nuvem→dispositivo — mesmo fallback antes de reportar `failed`).
- **Validado**: `tsc --strict`/build limpos. A lógica de execução sequencial (`executePlanSteps`, extraída à parte especificamente pra ser testável sem depender da chamada de rede) foi validada com um harness sintético rodando dentro de um processo Electron real (necessário porque o Audit Log depende de `app.getPath`): dois passos de sucesso em sequência rodam os dois; um passo de sucesso seguido de um de falha para exatamente ali, nunca chamando um terceiro passo depois; `argsJson` malformado vira falha imediata, também sem chamar o passo seguinte. **Não pôde ser validado nesta sessão**: uma chamada real ao endpoint de nuvem (rede deste sandbox não alcança produção, mesma limitação de sempre) nem o julgamento real do LLM decompondo um comando de verdade.

**Auditoria completa na nuvem** (roteiro original da arquitetura, "Fase I" — não confundir com a Fase 10F acima):
- O Audit Log LOCAL (`audit-log.ts`, Fase 10F) já existia; agora, além de gravar no JSONL local, cada entrada é sincronizada **best-effort** pra nuvem (`POST /api/presence/agent/audit`, repositório principal, tabela `agent_audit_log` aplicada e validada ao vivo — RLS de isolamento, imutabilidade e constraint testadas com dados descartáveis). "Best-effort" no sentido literal: sem pareamento, sem rede, ou erro do servidor — qualquer falha é silenciosamente ignorada (`.catch(() => undefined)`), **nunca** bloqueia nem derruba a execução real da ferramenta. O log local continua sendo a fonte de verdade.
- `cloud-client.ts` ganhou `sendAuditEntry()`, mesmo padrão de autenticação de dispositivo de sempre.
- A própria usuária consegue ver o que o Presence fez em Settings → Desktop Agent ("O que o Presence fez", repositório principal) — só leitura, ela nunca edita uma entrada.
- **Validado**: migration aplicada e testada ao vivo com dados descartáveis (RLS de isolamento entre 2 usuárias reais confirmada, tentativa de update via sessão autenticada afetando 0 linhas — imutabilidade —, tentativa de insert direto pela sessão autenticada rejeitada com `42501` real, `risk_tier` inválido rejeitado pelo check constraint). `tsc --strict`/build limpos no lado cliente; harness sintético dentro de um processo Electron real confirmando que `executeTool()` nunca trava esperando a nuvem e que uma falha de sincronização (sem pareamento, aqui) nunca vira uma `unhandledRejection`. **Não pôde ser validado nesta sessão**: uma sincronização real bem-sucedida (depende de pareamento real + rede que este sandbox não alcança).

**WhatsApp (roteiro original, "Fase J")** — opt-in explícito, risco real de banimento de conta (viola os Termos de Serviço do WhatsApp) **aceito conscientemente pela Jheny** (`AskUserQuestion` direto, 2026-08-23) antes desta implementação começar. Depois da fundação de conexão, ela pediu explicitamente pra continuar com a integração completa — leitura, busca, envio, integração com Planner/Permission Manager/Audit Log — sem parar de novo pra aprovação:
- **WhatsApp Renderer** (`src/whatsapp-window.ts`) — `BrowserWindow` oculta DEDICADA e ISOLADA de propósito, mesma arquitetura aprovada do STT Renderer: se esta parte quebrar (mudança de layout da Meta, sessão expirada) ou travar, nunca derruba wake word/controle/scheduler/fila de comandos/planner. Carrega `https://web.whatsapp.com` real (`session` com `partition: "persist:whatsapp"` — o próprio WhatsApp Web guarda a sessão de login nesse perfil isolado do Electron; este código nunca lê nem guarda nenhuma credencial por conta própria). Login inicial exige escanear um QR code — a janela fica oculta por padrão e só é revelada sob demanda (bandeja → "Conectar WhatsApp", ou o botão "Conectar" na janela de status).
- **Reconexão segura** — `did-fail-load`/`render-process-gone` disparam um reload com backoff crescente (5s/10s/20s/40s/60s); a sessão em si mora na `partition`, não na janela, então recriar/recarregar nunca perde login já feito. Um watcher (`startWhatsAppStatusWatcher`, a cada 15s) observa transições de status e detecta desconexão (`"connected"` → outra coisa); nunca tenta relogar sozinho (não há credencial que este código possa usar) — só notifica (`show_notification`) pra a própria pessoa escanear o QR code de novo.
- **`whatsapp_connection_status`** (Nível 0, read_only) — heurística best-effort que verifica marcadores conhecidos no DOM (`not_started`/`connecting`/`awaiting_qr_scan`/`connected`/`disconnected`/`unknown`).
- **Ações reais** (`src/whatsapp-actions.ts`), todas via `executeJavaScript` na janela dedicada:
  - `whatsapp_list_chats`/`whatsapp_search_chats`/`whatsapp_read_messages` (Nível 0, read_only) — executam sozinhas, sem confirmação, exatamente como a Jheny pediu ("para ações de leitura, mantenha o fluxo automático").
  - `whatsapp_send_message` (Nível 2, `external_comm`) — passa pelo MESMO Permission Manager de sempre (Fase 10F), que já exige confirmação por padrão pra esse nível ("para envio de mensagens, mantenha obrigatoriamente a camada de confirmação"). Nenhuma lógica de permissão nova foi escrita — só a classificação de risco correta, que o Execution Engine já aplica pra qualquer ferramenta.
  - Zero mecanismo paralelo: as 4 ferramentas são registradas no MESMO Tool Registry de sempre, então já aparecem automaticamente no catálogo do Planner (`buildToolCatalog()` usa `listTools()`), já passam pelo MESMO Execution Engine (Audit Log local + sincronização best-effort pra nuvem, Fase I, incluídos de graça), e já são alcançáveis pela fila de comandos/voz (o resolvedor determinístico não bate com "manda mensagem pro fulano", então cai pro Planner, que pode escolher `whatsapp_send_message` do catálogo).
  - **Aviso de honestidade, o mesmo já usado em `claude_code_confirmation_check`**: os seletores de DOM usados (`data-testid`, classes `message-in`/`message-out`, os `contenteditable` de busca/composição) são inferidos de padrões publicamente conhecidos e historicamente estáveis do WhatsApp Web — **nunca confirmados contra uma sessão real** (este sandbox não alcança `web.whatsapp.com`, sem conta pra escanear QR code). Bem provável que precisem de ajuste no primeiro teste real. Cada função devolve `{ok:true, data}`/`{ok:false, error}` — nunca lança por causa de um seletor não bater.
  - **Achado real descoberto durante a validação, e corrigido**: uma navegação/reload disparada pelo mecanismo de reconexão pode invalidar o contexto de execução de uma chamada `executeJavaScript` em andamento, fazendo a promise nunca resolver nem rejeitar — mesma classe de problema já documentada em `tools/timeout.ts` (Fase 10E, `screenshot-desktop`). Corrigido reaproveitando o mesmo `withTimeout()`: toda ação tem um limite de tempo externo (20s), nunca trava a interação por voz/fila de comandos/planner inteira por causa de uma única ação do WhatsApp.
- **Validado com o método mais forte disponível dado que não há como testar a integração real**: harness sintético dentro de um processo Electron real confirmou — as 4 ações reais (`listChats`/`searchChats`/`readMessages`/`sendMessage`) falham graciosamente (`{ok:false}`) contra a URL real que falha de verdade neste sandbox (`ERR_TUNNEL_CONNECTION_FAILED`, rede bloqueada, confirmado), nenhuma `unhandledRejection`, e a classificação de risco correta (`read_only` sem confirmação, `external_comm` exigindo confirmação por padrão) confirmada diretamente contra o Permission Manager real. App completo (com WhatsApp incluído) validado de pé por 10s com auto-encerramento limpo (`app.exit`), sem erro novo. `tsc --strict`/build limpos.

**Ainda não implementado**: resumo de mensagens via IA (reaproveitaria o Planner/Lovable AI Gateway se pedido no futuro — não construído sem necessidade comprovada); nada do WhatsApp foi testado contra uma sessão real (depende de um Windows real + conta pra escanear QR code).

**Voz do Presence** (resposta em voz da interação por wake word/duas palmas) — pedido explícito da Jheny depois de validar a integração real de WhatsApp/apps nesta máquina:
- **Response Composer** (`src/response-composer.ts`) — descreve, em português, o resultado JÁ executado de um comando (resolvedor determinístico ou Planner), nunca decide nem executa nada. Reconhece as ferramentas de WhatsApp especificamente (lê a lista de conversas/mensagens de dentro do `result` e monta uma frase falável) e cai num resumo genérico ("Pronto: X.") pra qualquer outra ferramenta.
- **`speech-output.ts`** — pede a síntese de voz à nuvem (`requestSpeech`, novo endpoint `POST /api/presence/agent/speech` no repositório principal, device-autenticado, reaproveitando a MESMA voz oficial ElevenLabs do app web — nenhuma voz nova/paralela) e publica um evento com o áudio em base64. Best-effort de propósito: uma falha de voz nunca derruba a execução real do comando, que já aconteceu antes.
- Como não existe API de áudio no Main Process do Electron, quem toca de verdade é o Renderer (`renderer/renderer.js`, `new Audio("data:audio/mpeg;base64,...")`) — o Main só encaminha os bytes por IPC (`agent:speech-audio`).
- Wireado só em `voice-interaction.ts` (wake word/duas palmas → comando falado → executado → resposta falada) — o comando digitado pelo site/fila de comandos continua só mostrando texto, sem voz, por design (modalidades diferentes).
- **Não pôde ser validado nesta sessão**: reprodução de áudio real depende de hardware (alto-falante) e de uma chamada de rede bem-sucedida à ElevenLabs, nenhum dos dois alcançável deste sandbox. A composição de frases foi revisada por leitura de código, não testada contra um resultado real de ferramenta.

## Instalar (recomendado — sem precisar mexer em código)

Baixe o instalador (`Presence-Setup-x.y.z.exe`) da aba [Releases](https://github.com/jhenyalvesc-lab/presence-desktop-agent/releases) deste repositório e rode. Isso instala o Presence de verdade no Windows (atalho, item na bandeja) — não é mais necessário `git pull`/`npm install`/rebuild manual a cada mudança.

**Atualizar depois de já instalado:** o próprio app confere sozinho a cada 6h (e uma vez ao abrir) se existe uma versão nova nos Releases. Quando uma atualização termina de baixar, a bandeja ganha o item "Reiniciar e atualizar (versão x.y.z)" — clique nele (ou peça pelo botão "Verificar atualização" na janela de status pra checar na hora). Nenhuma conta/senha nova envolvida — os Releases são públicos, a checagem não usa nenhuma credencial sua.

## Rodando a partir do código-fonte (desenvolvimento)

```bash
npm install
npm run rebuild-native   # uma vez, depois de instalar — recompila módulos nativos (ex. node-window-manager) contra o ABI do Electron
npm run start
```

Isso compila o TypeScript (`tsc`) e abre o Electron. Na primeira execução, sem pareamento ainda, a janela mostra um botão "Parear" — clique, um código de 6 dígitos aparece, e você o digita em Settings → Desktop Agent no app web do Presence (`spark-mind-friend.lovable.app`) enquanto estiver logada. Depois de aprovado, a janela mostra o dispositivo pareado e um botão "Ping" pra confirmar a comunicação de ponta a ponta.

Rodando assim (`npm run start`, não instalado), a checagem automática de atualização fica desativada de propósito — não existe instalador local pra atualizar.

## Publicar uma nova versão (pra quem mantém o código)

```bash
git tag v0.2.1
git push origin v0.2.1
```

Isso dispara `.github/workflows/release.yml` num runner Windows do próprio GitHub: instala dependências, recompila os módulos nativos, roda a checagem de tipos e publica o instalador como GitHub Release via `electron-builder --publish always` — sem precisar de um Windows real à mão pra compilar. Suba a versão em `package.json` antes de criar a tag (o número da tag e da versão publicada devem bater).

Por padrão aponta para `https://spark-mind-friend.lovable.app`. Para apontar para outro ambiente (ex. desenvolvimento local do backend), defina `PRESENCE_CLOUD_URL` antes de rodar.

Pra "abre X" funcionar de verdade, copie `config/app-registry.example.json` pra `config/app-registry.json` (ignorado pelo git — específico da sua máquina) e preencha com os caminhos reais dos seus aplicativos.

## Limitações conhecidas

- Validado por verificação de tipos (`npm run typecheck`) e por execução real do Electron sob `xvfb-run` (display virtual) neste ambiente de escrita — confirma que Main/Tray/Audio Worker sobem sem exceção e que os estados de status se comportam como esperado. **Não há microfone real neste ambiente** (`PvRecorder failed to initialize` é o erro esperado aqui, não um bug) nem Windows real — a validação de ponta a ponta com hardware de verdade depende de rodar isto num Windows de verdade.
- Wake word ("Presence") depende de uma AccessKey pessoal do Picovoice Console + um arquivo `.ppn` custom treinado — nenhum dos dois existe ainda; sem eles o Audio Worker roda com wake word desativada (`not_configured`), sem quebrar o resto do agente.
- Duas palmas: a lógica de DSP foi validada com dados sintéticos (sem hardware envolvido), mas os valores padrão de sensibilidade/janela de tempo nunca foram calibrados contra um microfone/ambiente real — bem provável que precisem de ajuste depois do primeiro teste real no Windows.
- STT (Fase 10D): a Web Speech API pode simplesmente não funcionar no Electron em produção (ver risco acima) — não confirmado nem descartado, só um teste real resolve.
- Controle do computador (Fase 10E): `list_windows`/`focus_window`/`close_window` não puderam ser validados de ponta a ponta (biblioteca sem suporte real a Linux); `open_app`/mouse/teclado foram validados de verdade neste sandbox, mas contra apps/registro de teste, nunca contra os aplicativos reais da Jheny. `npm run rebuild-native` ainda não foi executado num Windows real — o risco de incompatibilidade de ABI é teórico, baseado em números de versão confirmados, não num crash observado.
- Claude Code/GitHub (Fase 10H): `github_pr_status`/`github_actions_status` nunca foram testados com um `GITHUB_TOKEN` real (só o caminho de erro sem token). `claude_code_confirmation_check` é uma heurística best-effort — a arquitetura já reconhece que não existe solução garantida pra isto; o padrão de nome de processo e de título de janela não foi calibrado contra o Claude Code real da Jheny no Windows dela.
- Fila de comandos nuvem→dispositivo: o caminho de sucesso (comando real chegando via `/poll`, sendo executado e reportado via `/complete`) nunca foi testado de ponta a ponta — exige um dispositivo pareado de verdade, o que exige um Windows real. A rede deste sandbox não alcança o backend em produção nem pra provar o round-trip HTTP isolado.
- Planner: nunca chamou o endpoint de nuvem de verdade (mesmo isolamento de rede do sandbox) — a decomposição real de um comando composto pelo LLM (ex. "prepara meu ambiente de trabalho") nunca foi observada; só a lógica de execução sequencial dos passos foi validada com dados sintéticos.
- Auditoria completa na nuvem: nunca sincronizou uma entrada real com sucesso (sem pareamento/rede neste sandbox) — só o caminho de falha silenciosa (best-effort) foi validado de verdade.
- WhatsApp: nunca carregou o WhatsApp Web real (rede bloqueada neste sandbox) nem escaneou um QR code de verdade — só a mecânica de janela/isolamento/reconexão e a lógica de falha graciosa das ações foram validadas. TODOS os seletores de DOM usados (`whatsapp_connection_status` e as 4 ações reais) são inferidos, nunca confirmados contra uma página real; é praticamente certo que precisem de ajuste no primeiro teste real — não é "se", é "quando". Resumo de mensagens via IA não implementado (sem pedido/necessidade comprovada ainda).
- **Empacotamento/auto-update implementado** (`electron-builder` + `electron-updater`, ver seções "Instalar"/"Publicar uma nova versão" acima) — **nunca rodou de ponta a ponta neste sandbox** (sem Windows real, sem conseguir publicar um Release de verdade daqui): a primeira tag publicada por CI é quem prova se o instalador/atualização funcionam contra uma máquina real. Sem assinatura de código ainda — o instalador vai gerar o aviso padrão do Windows Defender/SmartScreen ("editor desconhecido") até isso ser resolvido (exige um certificado pago, decisão fora de escopo desta rodada).
- Ícone da bandeja é um placeholder mínimo (círculo sólido), sem identidade visual definida ainda — o mesmo arquivo é reaproveitado como ícone do instalador/app por ora.
